0Read this first: the basic ideas in plain words

This guide assumes you are a complete beginner. Before the technical chapters, here is the whole project explained with an everyday comparison. Come back to this page whenever a later chapter feels confusing.

The restaurant comparison
  • The market where ingredients come from = the data sources on the internet (FotMob, Understat).
  • The shopper who buys ingredients and stores them in the pantry = the scraper (scrape_fotmob.py) and its cache folder.
  • The kitchen that cooks the ingredients into dishes = the build step (build_dataset.py): it turns raw data into neat, ready-to-serve files.
  • The head chef who tastes every dish before it leaves = the verification step (verify_dataset.py).
  • The plates arranged on the counter = the JSON files in public/data/.
  • The waiter and the dining room = the website (frontend): it takes what you ask for and presents the right plate nicely.
  • The building, its address and its doors = Vercel hosting: it keeps the restaurant open 24/7 at a public address (URL).
  • The recipe book with every change written down = Git and GitHub.
In our restaurant, all the cooking happens before the customers arrive. When a visitor opens the site, the dish is already on the counter, so service is instant and nothing can burn while they wait.

1The project in one page

What it is. A website that lists every player at every club in Europe's top five leagues and shows, for each player, real statistics for his whole career: totals per competition (league, domestic cups, European competitions, national team) and a season-by-season breakdown where every season is split into each competition he played.

How it works, in one sentence. A Python pipeline downloads real match data, turns it into clean JSON files, checks them against an independent source, and a Next.js (TypeScript/React) website hosted on Vercel reads those files and displays them.

2The starting plan

Before writing code we answered four questions. This is the framework to reuse for any project: What must it do → What limits us → What shape should the system take → What tools fit that shape.

2.1 Requirements (what you asked for)

  1. Real, correct data, collected from the internet, not estimated.
  2. Every player at every club in the top 5 leagues.
  3. For each player: cumulative career stats split by competition, and yearly stats where each year is split by competition (league, Carabao/EFL Cup, FA Cup, Champions League, Super Cup, national team…).
  4. Goal contributions and deeper stats: goals, assists, dribbles, and more.
  5. Verify the data again after collecting it.
  6. Website must work for anyone at any time, even with your laptop off; no errors.
  7. Save everything in the football-transfer-market repository.

2.2 Constraints (what limits us)

ConstraintConsequence for the design
Most football stats sites block bots (Cloudflare "Just a moment…" pages, HTTP 403/405).Pick a source that serves JSON to normal requests; don't fight anti-bot systems.
No source publishes "official" data for all 5 leagues + all cups + Europe in one place.Use one consistent aggregator (Opta data via FotMob) and cross-check it with an independent one (Understat).
~2,700 players × many seasons × many competitions = tens of thousands of requests.Cache every response on disk, run in parallel with a rate limit, make it resumable.
Site must work with your laptop off, free hosting, no server to maintain.Pre-compute everything; serve static JSON files from Vercel's CDN. No live backend.
Limited tokens / time.Build one example player end to end first, then run the same code for everyone.

2.3 The design decision: a "static data site"

There are two common shapes for a data website:

Option A: live backend (what the first version tried) Browser → API server (FastAPI) → database (SQLite/Postgres). Needs a server running 24/7, costs money, breaks when the server/laptop is off; the first version even pointed at 127.0.0.1:8000 (your laptop).
Option B: pre-built static data (what we chose) Pipeline builds JSON files once → files are deployed with the website → browser downloads only the file it needs. No server to crash, free, very fast, works with the laptop off. Trade-off: data updates when you re-run the pipeline.

Player stats change at most once per match day, so "rebuild and redeploy" is a perfect fit. This is the single most important architectural choice in the project.

5Where we started: what was wrong

The first version (built with another agent) looked complete but the numbers were unreliable. Reading the code found the root causes. Lesson: when data "looks wrong", read the code that produced it before collecting new data.

Problem foundEvidenceEffect on the site
Projected, not real, statsfetch_api_football.py: "free tier only allows up to 2024. We will fetch 2024 and mathematically project it to 2026", ages +2Every 2026 number was an estimate.
Invented contract dataRelease clauses, wages (default €35,000/week), buy-back clauses had no sourceFinancial figures were fiction.
Stale squadsClub list hard-coded for 2024/25 (Ipswich, Leicester, Southampton…)Wrong clubs/leagues for many players.
Fake "sync" button/api/sync returned "success … synchronized" whenever the backend was unreachableClaimed updates that never happened.
Backend on your laptopBACKEND_URL default http://127.0.0.1:8000On Vercel this always failed silently and fell back to bundled data.
Unknowns turned into zerosSchema defaults like assists = Column(Integer, default=0)"0 assists" displayed where the truth was "unknown".
Only top scorers/assisters fetchedEndpoints topscorers, topassistsMost players had no real stats at all.
One 14 MB file loaded by every API callimport rawPlayers from "@/data/players.json"Slow functions, hard to scale.
The general lesson A system that silently "falls back" or "fills in" values is the most dangerous kind: it never shows an error, so you don't notice the data is wrong. Our rebuild follows one rule everywhere: if the source doesn't have a number, store null and show "–"; never invent, never default to 0.

🧰 What we used to diagnose, and why

ThingHow we used itWhy this, and not something else
Reading code before collecting new dataOpened the old fetch_api_football.py, live_updater.py and API routes.Found the real cause (projected numbers) in minutes. Collecting new data on top of a broken process would have repeated the problem.
Root-cause tableWrote each problem with its evidence and effect.Turns "the data feels wrong" into a concrete fix list.
The null ruleDecided: unknown values are null and shown as "–".A visible gap is honest; a fake 0 or estimate is a silent lie that nobody notices.

7Pipeline stage 1: collecting the data

File: backend/pipeline/scrape_fotmob.py (Python). It has three stages you run in order:

python scrape_fotmob.py squads                       # 5 leagues → 96 clubs → 2,707 player ids
python scrape_fotmob.py profiles --workers 10        # 2,707 career profiles
python scrape_fotmob.py deep --workers 10 --seasons 4 # 25,628 detailed-stat entries
python scrape_fotmob.py deep --player 737066          # any stage, one player only (the Haaland example)

7.1 The core algorithm: a cached, rate-limited, retrying fetch

Figure 3. The fetch() function, the heart of the scraper. Every one of the ~28,400 requests goes through it.

7.2 Why each piece exists

TechniqueProblem it prevents
Disk cache (one JSON file per request)Re-downloading after a crash; hammering the source. A stopped run simply continues; a second run is instant.
Atomic write (write .tmp, then os.replace)A half-written file if the process dies mid-write, which would otherwise be treated as valid cache.
Thread pool (10 workers)Waiting on network latency one request at a time. First run did 0.7 profiles/s; with 10 workers ~8 requests/s (25,628 entries in ~50 min).
Global rate lockWorkers bursting together; keeps total rate polite no matter how many threads.
Retry with back-off on 429/5xxLosing data to temporary server hiccups.
Trimming responses to needed keysDisk usage: raw profile ~140 KB, deep stats ~130 KB (shot maps, heat maps). Trimmed cache is ~110 MB instead of ~4 GB.
Null-safe trimmingThe run crashed at 25,603/25,628 because FotMob answered null for a few entries. Now an empty answer is stored as "no stats".
--player optionTesting on one player (Haaland) before spending ~1 hour on everyone.

7.3 The real code (simplified)

def fetch(path, params, cache_file, trim=None):
    if os.path.exists(cache_file):                 # 1. cached? done
        return json.load(open(cache_file))
    for attempt in range(5):
        with _rate_lock:                           # 2. one request at a time leaves the gate
            wait = _last_call[0] + MIN_INTERVAL - time.time()
            if wait > 0: time.sleep(wait)
            _last_call[0] = time.time()
        r = session.get(f"{BASE}/{path}", params=params, timeout=30)
        if r.status_code == 200:
            data = trim(r.json()) if trim else r.json()
            write_atomically(cache_file, data)     # 3. .tmp then os.replace
            return data
        if r.status_code in (429, 500, 502, 503, 504):
            time.sleep(5 * (attempt + 1)); continue  # 4. back off and retry
        return None                                # 5. 404: nothing there

7.4 Which detailed stats are fetched

The profile's statSeasons lists, for each season, the competitions with detailed data and an entryId like "1-3" (season #1, competition #3). The deep stage takes the 4 most recent seasons and every competition flagged hasDeepStats, and saves each as cache/deep/<player>/<season>_<competitionId>.json. Older seasons are skipped to keep the run to about an hour; apps/goals/assists for all seasons already come from the profile.

🧰 What we used here, how, and why only this

ThingHow we used itWhy this, and not something else
Python requests.SessionOne reusable connection per thread for all HTTP calls.Reusing connections is faster than opening a new one per request.
Disk cache (JSON files)Every answer saved under cache/; checked first before any request.Crash-proof and polite: re-running costs nothing. A database would be overkill for "save this answer".
ThreadPoolExecutor (10 workers)Ran many downloads at the same time.Downloads spend most time waiting for the network, which threads handle well. asyncio would also work but needs more complex code.
threading.Lock rate limiterAll threads pass through one gate that enforces a minimum gap between requests.Keeps the total speed polite however many threads run. Without it, 10 threads could burst and get blocked.
Retries with back-offOn 429/5xx errors, wait longer each time and try again (max 5).Servers have brief hiccups. Giving up immediately loses data; retrying instantly makes it worse.
Atomic write (.tmp + os.replace)Write to a temporary file, then rename it in one step.A crash mid-write can never leave a broken file that later looks like valid cache.
argparse command-line optionssquads/profiles/deep stages, --workers, --seasons, --player.Run one stage or one player for testing without editing code.

8.1 Step B: season bucketing (the trickiest rule)

Club seasons are named 2025/2026, but other entries are named differently:

8.2 Step C: labelling competitions

  • Type by name patterns: continental (Champions League, Europa, Conference, UEFA Super Cup, Club World Cup…), domestic cup (Cup, Copa, Coppa, Pokal, Coupe, Shield, Supercopa, …mesterskap…), national team (by section), otherwise league.
  • Name from FotMob's league list. If the same name exists in several countries ("Bundesliga", "Premier League", "Super Cup", "Cup") the country is appended: Bundesliga (Austria) vs Bundesliga (Germany).

8.3 Step E: merging mid-season transfers

Dean Huijsen, 2023/24: FotMob's career lists Juventus, Serie A, 1 app and Roma, Serie A, 13 apps, but the detailed Serie A stats cover the whole season (14 apps). Attaching those detailed stats to both rows counted them twice. Fix: rows with the same competition in the same season merge into one row, "Roma / Juventus: 14 apps, 2 goals", with a per-club split kept underneath. This halved the career-vs-detailed disagreements and matches Understat (which reports the combined 14 apps, 2 goals).

8.4 Step F: how totals are calculated

Kind of statExamplesHow it is combined
Countsgoals, assists, minutes, shots, dribbles, tacklesSum of known values.
Rates and percentagesrating, pass accuracy %, dribble success %, save %Minutes-weighted average (a 90-minute game counts more than a 5-minute cameo). Never summed.
Unknown partsOld seasons where assists = "undefined"Total = sum of known values, field listed in incomplete; the site shows a * next to it.
# the "unknown is not zero" rule, from build_dataset.py
def num(v, as_float=False):
    if v is None or v == "" or v == "undefined":
        return None                       # unknown stays unknown
    f = float(str(v).replace(",", "").replace("%", ""))
    return f if as_float else int(round(f))

8.5 Notes added to rows

  • "Detailed stats cover 11 of 16 matches (qualifying / early rounds have no detailed data)": e.g. Europa League including qualifiers. The headline apps/goals/assists still include qualifiers.
  • "Match data shows 1 goal… the source's season summary differs": the two FotMob endpoints disagree for the same matches (usually the current season, before one side updates). We show both rather than silently picking one.

Notes on rowsText caveats stored with the data and shown on the site.Explains real gaps (qualifiers) instead of hiding them or guessing.

10Pipeline stage 3: verification

File: backend/pipeline/verify_dataset.py. "It looks right" is not verification. We check the data two ways and write the results to verification_report.json.

10.1 Internal checks (hard errors fail the run)

  • Every season's totals equal the sum of its competitions.
  • No negative appearances, goals or assists.
  • Every player in the index has a file. (Separate check: all 2,707 files have every field the website needs.)
  • Counted, not failed: where FotMob's two endpoints disagree on goals/assists (now explained by row notes).

Result: 0 hard errors.

10.2 Independent cross-check with Understat

Figure 6. Cross-check algorithm.
MeasureResult
Player-league-seasons compared (2023/24, 2024/25, 2025/26)4,734, of which 4,489 matched by name + club
Appearances agree4,449 / 4,489 = 99.1%

10.3 What the differences turned out to be

  • ±1 assist (Saka 9 vs 8, Damsgaard 10 vs 9): the two sources define assists differently. Opta's definition (FotMob) is the one leagues publish.
  • Big gaps at first (Vitinha PSG vs Vitinha Marseille, two "Toni Martínez"): our matcher paired different people with the same name. Fix: require the same club as well. Big gaps went from 7 to 1.
  • The last one (Amad Diallo 2023/24: 9 apps vs 1): Understat's record is incomplete; 9 is correct.
Lesson Verification can be wrong too. When a check fails, investigate whether the data or the check is at fault. Two of our "data errors" were actually bugs in the verifier and in the builder.

🧰 What we used here, how, and why only this

ThingHow we used itWhy this, and not something else
Independent source comparisonCompared 4,489 player-seasons with Understat.The only strong evidence that numbers are right: two independent collectors agree.

11The frontend: how the website works

11.1 Next.js App Router in 60 seconds

In Next.js, folders are URLs. src/app/page.tsx is /; src/app/players/[id]/page.tsx is /players/anything, with the square brackets meaning "a variable part of the URL". Files in public/ are served as they are, so public/data/index.json is available at /data/index.json.

Components are server components by default (rendered on the server/at build time). A file starting with "use client" runs in the browser and can use state, clicks and effects. We use:

app/layout.tsxserverHTML skeleton, Geist font, page title "Football Transfer Market".
app/page.tsxclientHome: loads index + meta, search box, league/position/club filters, sort, cards, "Show more".
app/players/[id]/page.tsxserverReads the id from the URL (in Next.js 16 params is a Promise: await params) and renders PlayerView.
app/players/[id]/PlayerView.tsxclientFetches the player file; header, KPI cards, two tabs, tables, expandable detail grids.

  5. verify_dataset.py fetches Understat EPL 2025: Erling Haaland, Manchester City, 27 goals. Match.
  6. Committed in public/data/players/737066.json, deployed to Vercel.
  7. The browser fetches the file and n(27) prints "27" in the Goals column.

17Lessons for your next project

17.1 A planning template (copy this)

QuestionThis project's answer
1. What exactly must the user see/do?Search players; see career + season stats split by competition.
2. Where does the data come from, and is it allowed and reachable?FotMob (Opta), Understat; tested with curl first.
3. How often does it change?After each match day → batch rebuild is fine.

17.2 Data and pipeline checklist

  • Look at real raw responses before writing transform code (several bugs came from guessing field names).
  • Cache every request; make every stage resumable; write files atomically.
  • Unknown ≠ 0. Keep null, show "–".
  • Never let a fallback silently pretend to succeed.
  • Watch for double counting when combining two views of the same data.
  • Separate counts (sum) from rates (weighted average).
  • Verify against an independent source, and verify the verifier.
  • Build one example end to end before scaling up.

17.3 Frontend checklist

  • Write the data shape as TypeScript types first; let the compiler check you.
  • Keep files small: one big file (the old 947-line page) is hard to fix; we split into page, view, table, grid, helpers.
  • Load only what a page needs (index vs one player file).
  • Design every state: loading, error, not found, empty, missing image.
  • Read your framework version's docs; Next.js 16 changed APIs (e.g. params is a Promise).
  • Run lint, build and a real-browser click-through before every deploy.

17.4 Deployment and security checklist

  • Deploy to preview, test, then promote. Never debug on production.
  • Never paste tokens or passwords into chats, code or commits; use environment variables; revoke anything exposed.
  • Use fine-grained tokens limited to one repository, with short expiry.
  • Don't commit generated or partial data; commit the verified final output.
  • Don't point production at localhost.

20Roadmap: how to build a project like this from zero

Follow these steps in order for your next data website. Each step has a clear "done when…" so you know when to move on. This is exactly the order used in this project, cleaned up.

Day 0

Step 1: Set up your tools

Install VS Code, Git, Python 3, Node.js (LTS). Create GitHub and Vercel accounts and connect them.
Done when: git --version, python --version and node --version all print versions in your terminal.
Day 1

Step 2: Write the requirements (one page)

What will a visitor see and do? What data exactly (which fields, which seasons, which players)? What does "correct" mean?
Done when: you have a numbered list like section 2.1, and a sketch of each page on paper.
Day 1–2

Step 3: Find and test the data source

List candidate sources. Test each with one request (curl or Python). Check that it has every field you need, and read its terms. Pick a primary source and a second source for checking.
Done when: you have one saved real response from your primary source and know which keys hold your data.
Day 2

Step 4: Choose the architecture with the planning questions

Use the template in section 17.1: How often does the data change? Does anyone write data? How big is it? Read-only and updated daily or weekly → static data site (this project). Users write data or it changes every second → backend + database.
Done when: you can draw your version of Figure 2.
Day 3–4

Step 5: Design the data files first

Write the JSON shape the website will read (like section 9) and the matching TypeScript types. Decide the rules: unknown = null, how totals work.
Done when: you have one hand-written example JSON file for one item (one player).
Day 4–6

Step 6: One example, end to end

Write the smallest scraper for ONE item, the transform that produces your example JSON, and a bare web page that displays it.
Done when: one real item shows correctly on a local web page. (Our version: Haaland.)
Week 2

Step 7: Make the scraper robust, then scale up

Add disk cache, rate limit, retries, atomic writes and stages. Run on 10 items, then all items.
Done when: a full run completes and a second run makes zero requests.
Week 2

Step 8: Verify the data

Write invariant checks (totals add up, nothing negative, every file present) and an independent cross-check. Investigate every big difference.
Done when: 0 hard errors, a high agreement rate, and every remaining difference explained.
Week 3

Step 9: Build the real website

Next.js app: list page (load index, search, filter, sort) and detail page (load one file). Handle loading, error, empty and missing-image states.
Done when: npm run lint and npm run build pass, and you've clicked through 20 pages by hand.
Week 3

Step 10: Test like a visitor

A Playwright script that opens the home page and many detail pages, clicks the controls, and records errors. Also check that every data file loads.
Done when: the script reports 0 errors.
Week 4

Step 11: Save, deploy a preview, test, go live

Commit to a branch and push. vercel deploy (preview), test it, then vercel promote (production). Test the live URL again.
Done when: the public URL works on your phone and on a friend's computer.
Afterwards

Step 12: Keep it fresh and improve

Write a README with run commands. Automate the refresh (e.g. a weekly GitHub Actions job). Add features one at a time, each with steps 6 → 11.
Done when: someone else could run the project from your README alone.

The three rules to remember if you forget everything else
  1. Look at real data before you build. Most bugs in this project came from assumptions about data shape.
  2. One example end to end, then scale. Small loops are fast to fix.
  3. Never fake a number, never skip the test. Show "–" for unknown; check against a second source; click through the real site before shipping.
